## 两项原则

```text
1. Every test names the break it catches
2. Every test exercises the real thing
```

测试应捕获一个具体破坏，并尽可能运行真实对象。先写测试并观察它针对真实代码失败，才能证明测试确实具有检测能力。

## 原则一：说出要捕获的破坏

在编写测试主体前，先回答：

> 哪项生产代码变更应该让这个测试失败？那项变更是 bug，还是仅仅改变了内部实现？

好的测试会捕获错误分支、遗漏的副作用、错误参数、边界情况或被破坏的契约。

### 独立推导期望值

使用字面量或人工检查过的 fixture。不要用被测代码或共享同一逻辑的 helper 计算 expected value：

```typescript
// 差：两边使用同一个 builder，可能永远相等
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// 好：人工推导期望值
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

### 测试行为，而不是变更探测器

不要只断言常量、精确文案或私有结构没有改变。测试依赖这些决策的可观察行为：

- 差：`expect(MAX_RETRIES).toBe(5)`
- 好：验证失败操作最多尝试五次，并且不会发生第六次调用

### 运行产物，而不是 grep 源码

对于脚本、配置或行为指导文档，应运行受控场景并断言输出、副作用、退出码或 Agent 行为。源码包含某一行，只能证明文本存在，不能证明行为有效。

面向人类的纯说明文字通常不需要自动测试。

### 测试自己的边界契约

测试代码在边界处建立的契约，如注册的路由、发出的请求、生成的 payload。不要重复测试框架维护者已经负责的机制。

构造函数、getter、常量和简单转发只有在它们执行验证、规范化、默认值、推导、约束或副作用时才值得单独测试；否则测试第一个用户可见结果。

### 编写测试前的关卡

```text
说出会让测试失败的生产代码变更。

无法说出                  → 围绕可观察行为重新设计
只能说“源文本变了”        → 运行产物并断言效果
只有有意内部决策会触发     → 测试依赖该决策的行为

确认 expected value 未复用被测逻辑。
如果复用了：
  改为字面量或人工检查的 fixture。
```

## 原则二：运行真实对象

### 不要让 mock 成为断言目标

只证明 mock 存在的断言没有验证真实组件：

```typescript
// 好：真实可观察行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// 差：只证明 mock 被渲染
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

如果断言对象是 mock，优先取消 mock 或删除没有价值的断言。

### 在正确层级 mock

替换真实方法前，先列出它的全部副作用。只 mock 缓慢、外部或不稳定的边界，保持测试依赖的状态变化真实。

```typescript
// 差：mock 吞掉了 duplicate detection 所依赖的配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// 好：只 mock 缓慢的 server startup，配置写入仍真实
vi.mock('MCPServerManager');
```

不确定时，先针对真实实现运行测试，观察哪些副作用是必要的。

### 让 test double 具体化

当参数、调用次数或顺序属于公开契约时，对它们作出具体断言。为成功、错误、格式错误等分支提供各自 fixture，使错误分支无法意外满足成功期望。

### 完整镜像真实数据

mock response 应包含真实结构中所有相关的已文档化字段，而不是只包含当前测试读取的字段。残缺 mock 会让下游读取遗漏字段时出现“测试通过、集成失败”。

### 仅供测试使用的逻辑留在测试工具

只为测试清理而存在的方法，不应加入生产类。判断：

- 它是否只从测试调用？
- 生产对象是否真的拥有该资源的生命周期？

若答案不支持生产职责，把逻辑放进测试 helper 或 fixture。

### mock 膨胀时使用真实组件

当 mock setup 比测试主体更长、mock 经常遗漏真实方法，或 mock 的内部变化频繁破坏测试时，改用真实组件的 integration test。

### 添加 mock 前的关卡

```text
列出真实方法的副作用。
保留测试依赖的副作用真实，只在更外层 mock 缓慢或外部操作。

让 mock response 镜像完整结构。
仅供测试使用的逻辑放在测试工具中。

正准备断言 mock 本身？
  取消 mock，或删除该断言。
```

## 测试与实现一同交付

失败测试、最小实现、重构共同构成一个行为的完成。只交付保护该行为所需的测试。不要为了覆盖率给无行为的样板或人类说明文字增加永久维护成本。

## 变异检查

完成前，在脑中变异生产代码；每个现实的错误变异至少应让一个测试失败：

- 错误的常量或参数；
- 错误的分支 handler；
- 缺失的状态变化或副作用；
- 空值或默认返回值；
- 缺少对零、空、nil、未授权或 malformed input 的校验。

如果没有测试能捕获某个现实破坏，该行为尚未受到保护；如果测试对任何破坏都不敏感，它可能只是同义反复。

## 快速参考

| 当你…… | 应当 |
|---|---|
| 编写测试 | 说出它捕获的 bug，而非内部决策 |
| 构建期望值 | 人工推导，不使用被测代码 |
| 测试脚本或行为文档 | 运行它或压力测试使用者，不 grep 文本 |
| 测试依赖 | 测试自己的边界契约 |
| 想断言 mock | 使用真实组件或取消 mock |
| 准备 mock 方法 | 先理解全部副作用 |
| 构建 mock response | 镜像真实完整结构 |
| 需要测试专用清理 | 放进测试工具 |
| mock setup 膨胀 | 使用真实组件的 integration test |
| 完成测试文件 | 做变异检查 |

## 警告信号

- setup 与 assertion 共享同一个对象，保证相等；
- 测试只能因 crash、panic 或缺少 selector 而失败；
- 每次内部重构都会失败，却捕获不了真实 bug；
- expected value 隐藏在 loop、builder 或 helper 后；
- 测试只 grep 源文本；
- 即使删掉业务代码只剩框架，测试仍能通过；
- 测试只为覆盖率存在，不检查结果或副作用；
- 断言检查 `*-mock` 元素；
- 某个生产方法只从测试调用；
- mock setup 占测试主体的一半以上；
- 无法解释为什么需要某个 mock。
